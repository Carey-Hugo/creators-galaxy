## 核心原则：Burn tokens, not headcount

> 原文：Tom Blomfield (YC GP) · "Burn tokens, not headcount"
> 翻译：烧API账单，不烧人头。

**方向**：不是省token，而是搞清楚新智能到底能做到什么。
一个会用AI的人 + Agent系统 = 过去一个团队。
宁可承担让你"不舒服"的API账单，因为它替代的是更贵、更慢、更臃肿的人力。

## 一、模型路由策略：10/90原则

### 决策树

```
架构设计 / 系统安全审查 / 跨模块复杂重构
    → Opus 4.6 / GPT-5（仅占10%任务，差价可忽略）

常规开发 / 代码审查 / 调试 / 重构 / 功能实现
    → Kimi 2.6（月之暗面，主力日常，成本仅Sonnet的1/6）

代码格式化 / 单行修改 / 简单修复
    → Claude Haiku 4.5 或本地Ollama

模板代码 / 自动补全 / 语法修复
    → 本地模型（通义千问3 / Llama3 via Ollama），零成本
```

### 为什么Kimi 2.6是2026年默认最优选择

| 指标 | Kimi 2.6 | Claude Sonnet 4.6 | 差距 |
|------|---------|-------------------|------|
| 输入价格 | $0.5/M | $3/M | Kimi便宜6x |
| 输出价格 | $2/M | $15/M | Kimi便宜7.5x |
| 重构500行 | $0.04 | $0.12 | 质量相当 |
| 迭代30轮 | $1 | $25 | Opus $25 |
| 限流 | 配额充足 | 高峰限流 | Kimi更稳 |

> 2025年"Kimi=廉价平替"的认知已过时。2026年它才是主力最优选择。

## 二、上下文管控：真正的降本杠杆

### 问题根源
你付费的不是"修复Bug"，而是让AI反复读取整个仓库，只为找到30行关键代码。

### 操作原则

**① 检索优先，再加载**
```
# 不用"以防万一"加载全部文件
# 先grep定位，再只发相关片段
rg "目标函数名" --type py -l           # 找到文件
rg "目标函数名" --type py -B5 -A20   # 找到上下文
```

**② 关闭不必要的自动上下文**
- Cursor：禁用@codebase全局读取，改精准@文件调用
- Claude Code：优先用内置检索工具，而非一次性全仓库
- 子Agent任务：只传相关文件片段，不传整个项目描述

**③ 长对话定期精简**
- 每10-15轮，让AI总结进度+丢弃冗余历史
- 20万Token对话可精简至5000Token，后续成本仅为原来的5%

**④ 批量处理零散请求**
- 10个小问题合并为1次提问，避免多次输入计费
- 批量任务输入Token减少70%-90%

## 三、工作流优化：减少无效循环

### 5个隐形Token陷阱（逐条修复）

**陷阱1：每轮对话重复发送完整仓库代码**
- 问题：Cursor/Claude Code自动加载30-50个未变更文件
- 修复：关闭稳定文件自动上下文，仅通过prompt缓存加载一次
- 降本：稳定开发场景输入Token减少60%-80%

**陷阱2：智能体工具调用无限循环**
- 问题：每轮问答内，5万Token上下文被重复计费5次
- 修复：批量执行关联工具调用；固定工作流用Python脚本替代Agent循环
- 降本：智能体工作流成本降低3-5倍

**陷阱3：高端模型处理低端任务**
- 问题：用Opus改错别字、格式化JSON，0.6美元 vs Haiku仅0.02美元
- 修复：路由分层（见第一节）
- 降本：格式/清理类任务降本95%

**陷阱4：该批量却流式，该流式却批量**
- 修复：稳定固定上下文用批量模式；交互式编码开启流式；后台Agent用批量

**陷阱5："以防万一"加载冗余文件**
- 修复：让AI主动申请需要的文件，不主动冗余投喂

## 四、提示词缓存：被严重低估的降本手段

**原理**：缓存Token仅为常规输入价格的10%

**操作**：
```
Claude Code：系统指令 + CLAUDE.md 自动缓存
Cursor：设置→模型→开启提示词缓存
Aider：启动参数添加 --cache-prompts
```

**策略**：把稳定上下文（CLAUDE.md、系统指令、仓库概述）放入缓存前缀，以5分钟为单元拆分工作（匹配缓存有效期）。

**降本**：稳定输入Token减少60%-90%

## 五、工作流沉淀：SKILL.md是降本复利

**原则**：工作流跑通后，立即保存为SKILL.md。下次智能体直接读取，跳过摸索阶段。

**效果**：
- 部署预发布环境：Opus单次$4 → 沉淀文档+Kimi后单次$0.18
- 每次复用节省$3.82，且速度更快

**实践**：
- Hermes Agent的skill系统就是这个逻辑
- 公众号文章→封面→合成→HTML，已沉淀为cghub-wechat-article技能
- 每个跑通的OPG工作流，都应该写成skill

## 六、本地模型兜底：零成本模板处理

**工具**：Ollama部署通义千问3/Llama3

```bash
brew install ollama
ollama pull qwen3:7b
ollama serve
# IDE指向 localhost:11434
```

**用途**：

- 语法修复

- 简单格式调整

**不适合**：复杂推理、质量敏感任务

**降本**：模板类任务100%免费

## 七、30天落地计划

### 第1周：止损
- 全工具开启提示词缓存
- 关闭稳定文件自动上下文
- 安装ripgrep，检索优先
- **目标降本：30%-40%**

### 第2周：路由切换
- 配置Kimi 2.6为默认模型
- 格式化任务切Haiku
- Opus/GPT-5仅用于架构规划
- **目标额外降本：40%-55%**

### 第3周：修复循环
- 开启工具调用日志
- 修复3个最高耗循环
- 批量调用替代重复循环
- **目标额外降本：10%-20%**

### 第4周：沉淀+本地
- 沉淀3个高频工作流为SKILL.md
- Ollama部署通义千问3
- **目标额外降本：5%-10%**

**累计：70%-85%降本，开发速度不变**

## 八、什么时候必须用高端模型

降本不是无底线省钱。以下场景错误代价 > 模型差价100倍：

- 系统架构设计
- 生产环境安全审查
- 跨模块复杂重构
- 并发/竞态问题调试
- 编译器/形式化验证

**判断原则**：这个决策的错误代价 > 模型差价×100倍，就用高端模型。
