## 五、竞品差异化策略

### Hey（Lens应用）——个人主页UI参考

**学习点：**
- Next.js + TypeScript + GraphQL 技术栈
- 简洁的创客主页设计
- Lens Profile 集成

**CGHub超越点：**
- 不只是展示，要做价值记录
- 主页=个人品牌+作品集+收入来源
- Lens + Safe 双集成

### Paragraph——创客变现机制参考

**学习点：**
- 订阅模式（$5/月）
- 打赏功能
- 创作者收入透明

**CGHub超越点：**
- 分配规则预先锁定（Paragraph是事后打赏，CGHub是事前合约）
- 贡献记录可追溯
- OPC合伙人机制（类Gitcoin空投逻辑）

### Gitcoin——声誉系统参考

**学习点：**
- QF（二次方资助）
- 贡献者档案+历史
- 资助轮次机制

**CGHub超越点：**
- Gitcoin是资助，CGHub是协作分配
- Gitcoin是中心化审核，CGHub是智能合约自动执行
- 贡献实时记录，不是轮次制

### Safe——AI钱包参考

**学习点：**
- 多签钱包（3/n）
- 模块化架构
- AI Agent托管可能性

**CGHub超越点：**
- Safe是通用钱包，CGHub是创客专用
- Safe需要自己管理，CGHub有AI Agent辅助
- Safe + CGHub = 创客完整解决方案

## 七、关键设计决策（基于竞品分析）

### 决策1：身份系统——先Lens还是先自建？

```
结论：先自建身份+Lens绑定，双轨并行

理由：
- 自建身份保证主权（不被Lens绑定）
- Lens绑定获得社交图谱（裂变增长）
- 借鉴Hey的模式：个人主页同时支持Lens Profile

风险：
- Lens生态不稳定
- 应对：接口抽象，随时可切换
```

### 决策2：分配机制——用现有合约还是自研？

```
结论：优先集成Safe合约，自研核心分配逻辑

理由：
- Safe经过审计，安全可靠
- Safe多签功能完善
- 自研分配合约风险高
- 借鉴Gitcoin的贡献记录逻辑

风险：
- Safe功能有限制
- 应对：Safe Module机制扩展
```

### 决策3：代币经济——有无代币？

```
结论：短期无代币，长期船票代币化

理由：
- Hackathon阶段无代币更易通过
- v1.0阶段用"贡献积分"代替代币
- v2.0考虑代币化（船票=治理代币）
- 借鉴Nouns DAO的PPG系统

风险：
- 无代币用户激励弱
- 应对：贡献记录+声誉系统替代
```
